# market-making

**Does a simple passive market maker have an edge on the Bybit BTCUSDT linear perpetual,
and where does its PnL actually come from?**

This repo is a research framework to answer that honestly. It downloads and validates
Bybit's full-depth order book history, records the live feed, replays both through an
event-driven fill simulator with explicit latency, post-only and queue assumptions, and
splits PnL into **spread capture / inventory / fees**, with **fill markouts** to measure
adverse selection. The strategy, simulator and analytics are ported from an earlier
Hyperliquid project ([crypto-market-making](https://github.com/Stephane334R/crypto-market-making)),
so the two venues can be compared with the same code.

Public market data only. No API keys are used or stored.

## Headline results

All on **Bybit BTCUSDT linear perpetual, 2026-11-03 .. 2026-11-09 (UTC)**: 7 days, 433M
order book level updates, 11.6M trades.

| | result |
|---|---|
| **Data quality** | 0 sequence gaps, 0 crossed or locked books after rebuilding the book from snapshot + deltas. All 7 end-of-day snapshots match the rebuilt book level by level. Update ids are continuous across all 6 day boundaries. |
| **Strategy, held-out days** (2026-11-08, 09; parameters chosen on 11-03..07) | **−109 ± 164 USDT/day**, 1 of 2 days profitable: indistinguishable from zero, and the selected parameters sit at the edge of the grid. |
| **Edge** | None. All 56 configurations lose on the train days, and PnL improves monotonically as quotes widen, i.e. toward not trading. At an $8 half-spread the markout is +0.74 bps at the fill and −0.40 bps 100 ms later; fees (2 bps) are the largest cost near the touch. |
| **Fills** | 80–92% of fills are sweeps *through* our price, so the queue-position model changes PnL by < 1%. The result is robust to the queue assumption. |
| **vs Hyperliquid** (same code, same $8 setting) | Bybit loses more per day (−3,044 vs −1,405 USDT) and per unit volume (−2.83 vs −1.1..−2.1 bps) despite better markouts. Likely causes: a higher fee (2.0 vs 1.5 bps), ~8x more trades, and a finer book. |
| **Rust fill simulator** | Bit-identical fills and PnL to the Python simulator; **9.6x faster** (8.4 s vs 80.6 s for one day, 3.07M events). |
| **Live recorder** | 10-minute local test: 0 gaps; 8 of 8 aligned REST checks matched the local book exactly on 50 levels. A machine sleep caused a disconnect, which was recovered automatically. |

The honest reading: a naive vol-scaled quoter resting near the touch on BTC perps has no
edge on either venue. The loss comes from being swept (adverse selection) and from fees.
The next real experiment is a toxicity filter, not more parameter tuning. Details:
`results/<run_id>/summary.md` (generated by the commands below) and [LEARNING.md](LEARNING.md).

## Architecture

```
Bybit history archive ──► mm.download_bybit ──► data/raw ──► mm.normalize_bybit ──┐
  (ob200 deltas, trades)     (retries, cache)                (exact ints, Parquet) │
                                                                                   ▼
Bybit v5 websocket ──► rust/recorder ─────────────────────────► common schema Parquet
  (orderbook.1000, publicTrade)  (gap detect, resubscribe,          (docs/SCHEMA.md)
                                  REST cross-check)                       │
                                                                          ▼
                                 mm.validate (book rebuild, gaps, crossed books)
                                                                          │
        mm.strategy ──quotes──► mm.simulator (Python)  ◄── parity ──► rust/sim
                                      │                     (bit-identical, 9.6x faster)
                                      ▼
                     mm.analytics / mm.backtest / mm.report ──► results/<run_id>/
```

| Part | Language | Why |
|---|---|---|
| Downloader, normalizer, validator (`python/mm/`) | Python | Batch jobs, iterated on often; pyarrow handles the heavy I/O. |
| Strategy, simulator, analytics, backtest | Python | Research code that changes daily. The simulator is the readable reference implementation. |
| Live recorder (`rust/recorder`) | Rust | A long-running process that must not stall or leak: predictable latency and memory, clean shutdown, no GC pauses. |
| Fill simulator (`rust/sim`) | Rust | The replay loop is the bottleneck: 76M book updates per day. The port is held to **exact** parity with Python by tests, so speed never costs correctness. |

**One common schema** ([docs/SCHEMA.md](docs/SCHEMA.md)) is written by both the historical
pipeline and the live recorder: `book_updates` (one row per price level per message) and
`trades`. Prices and sizes are int64 ticks and lots, never floats; a value off the tick grid
raises instead of rounding. Tick and lot sizes travel in each Parquet footer.

## Data sources and their limits

| Source | What it gives | Limits |
|---|---|---|
| Bybit history archive, order book: `quote-saver.bycsi.com/orderbook/linear/...ob200.data.zip` | Snapshot + deltas, **200 levels, every 100 ms**, in the websocket format (500 levels before 2025-08-21) | Not part of the documented API (the host could change). **Conflated to 100 ms**: changes inside an interval are netted. No local timestamps. |
| Bybit history archive, trades: `public.bybit.com/trading/BTCUSDT/` | Every trade: time (0.1 ms), side, price, size, trade id | No trade sequence number, so **trade gaps cannot be detected**. Timestamps truncated to ms. |
| Bybit v5 public websocket (`rust/recorder`) | `orderbook.1000` (1000 levels, 200 ms) and `publicTrade`, with local receive time | Tested locally only (no VPS); the local clock offset is not measured. A resubscribe snapshot can be older than deltas already received (observed, handled). |
| Bybit REST `/v5/market/orderbook` | Top-N snapshot sharing the `orderbook.1000` update-id space | Used for the recorder's 60 s quality check only. |

**L2 only, queue position estimated.** Every source is price-level (L2) data: we see the
total size at each price, never individual orders. The simulator therefore *estimates*
our queue position:
- On joining a level, everything displayed there is ahead of us.
- Prints at our price consume the queue ahead first.
- Size decreases not explained by prints count as cancellations spread pro-rata over
  the queue.

It is labelled as an estimate everywhere, and the original fixed-ratio model is kept for
comparison. RPI (retail price improvement) orders are excluded from Bybit's public book.
None appear in the trade archive for these days.

## How to reproduce

Requirements: [uv](https://docs.astral.sh/uv/) (Python ≥ 3.11) and a Rust toolchain (stable).
About 3.5 GB of disk for 7 days. On a 4-core laptop with 2 GB RAM: ~50 min for step 1
(mostly downloading and parsing), ~16 min for step 2, ~3 min for step 3.

```bash
git clone https://github.com/Stephane334R/market-making && cd market-making

# 1. Data: download, normalize to Parquet, validate (report in results/validate_<UTC>/)
cd python && uv sync
uv run mm-bybit run --start 2026-11-03 --end 2026-11-09

# 2. Backtest: 5 train / 2 held-out days, 56 configs x 2 fill models (results/backtest_<UTC>/)
uv run python -m mm.backtest
uv run python -m mm.report ../results/backtest_<UTC>     # re-render summary.md

# 3. Rust: build, then benchmark Python vs Rust on 2026-11-09 (results/bench_sim_<UTC>/)
cd ../rust && cargo build --release && cd ../python
uv run python -m mm.bench_sim

# 4. Tests: Python + Rust. MM_RUN_REFERENCE=1 adds the full-day reference and
#    Rust-parity runs (need the data from step 1, ~5 min)
uv run pytest
MM_RUN_REFERENCE=1 uv run pytest
cd ../rust && cargo test --release

# 5. Live recorder (local test): 10 minutes into data/live/BTCUSDT/<session>/
cd .. && rust/target/release/recorder --minutes 10
MM_RECORDED_SESSION=data/live/BTCUSDT/<session> uv run --project python pytest tests/test_recorded.py
```

Every result folder contains a `config.json` with the dates, symbol, parameters, the
SHA-256 of each source file and the git commit. Each reference simulator output in
`tests/reference/` is checked by an exact re-run.

## Limitations

- **Short sample.** 7 contiguous days (5 train / 2 held out) of one regime. Per-day PnL is
  noise-dominated (one move on 2026-11-08 made that day's loss), and |t| < 1 on the held-out
  days. Results show the *shape* of the economics, not a precise number.
- **Queue position is estimated** from L2 data (see above), and the 100 ms conflation hides
  adds and cancels within an interval.
- **No market impact.** Our orders are not in the replayed book or tape.
- **Latency model.** Constant 50 ms from decision to live order, instant cancels, no jitter.
  The recorder's local timestamps use an unmeasured local clock.
- **Costs.** Bybit base-tier maker fee (0.02%); no rebates, no funding payments.
- **One clock.** Book `ts` (system time) and trade `T` (fill time) are merged as one
  exchange clock.
- **Sessions.** Each day starts flat; no overnight inventory.
- **Archive dependency.** The order book archive host is not part of Bybit's documented API.
- **Grid.** The best configuration is at the edge of the grid, i.e. "trade less". It is not
  an interior optimum.
- **Commit stamps.** The current result folders record the commit *before* the code that
  produced them (marked `-dirty`). Re-running the commands above stamps the exact commit.
